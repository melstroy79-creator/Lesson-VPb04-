# Архитектура системы управления задачами (Todo)

Документ-черновик для коллеги: что за объекты живут в системе, что они знают о себе
и как договариваются друг с другом. Код здесь не обсуждаем — только модель.

---

## 1. Главная идея

Систему делим на три слоя ответственности:

| Слой | Кто | За что отвечает |
|---|---|---|
| Данные | `Task`, `Project`, `User` | Хранят своё состояние и защищают его правила |
| Координация | `TaskManager` | Сценарии: «создать задачу», «перенести», «показать просроченные» |
| Хранение | `TaskRepository` (интерфейс) | Сохранение/загрузка, чтобы домен не знал про файлы и БД |

Правило: объект меняет **только свои** данные. Чужие данные меняются через методы владельца.

---

## 2. Классы

### 2.1 `Task` — атомарная единица работы

**Атрибуты**
- `id` — уникальный идентификатор (генерируется при создании, не меняется никогда)
- `title` — короткое название (обязательное, непустое)
- `description` — подробное описание (может быть пустым)
- `is_done` — флаг выполнения (по умолчанию `false`)
- `priority` — важность: `low | normal | high`
- `due_date` — срок (может отсутствовать)
- `created_at` — дата создания (ставится автоматически)
- `completed_at` — когда выполнена (`None`, пока не выполнена)
- `tags` — набор меток (`list[str]`, без дублей)

**Методы**
- `mark_as_done()` — выполнить: ставит `is_done = True`, фиксирует `completed_at`
- `reopen()` — вернуть в работу: `is_done = False`, `completed_at = None`
- `rename(new_title)` — переименовать с проверкой, что строка не пустая
- `change_description(new_text)` — заменить описание
- `change_due_date(date_or_none)` — сдвинуть или снять срок
- `change_priority(level)` — изменить важность
- `add_tag(tag)` / `remove_tag(tag)` — управление метками
- `is_overdue(now)` — просрочена ли (не выполнена и `due_date < now`)
- `to_dict()` / `from_dict(data)` — сериализация для хранения

**Правила (инварианты)**
- `title` не может быть пустым или состоять из пробелов.
- `is_done` меняется **только** через `mark_as_done()` / `reopen()` — снаружи поле не трогаем,
  иначе `completed_at` разъедется с флагом.
- `completed_at` заполнен тогда и только тогда, когда `is_done == True`.

---

### 2.2 `Project` — контейнер задач

**Атрибуты**
- `id`
- `name` — название проекта (обязательное)
- `description`
- `owner` — ссылка на `User` (кто создал)
- `tasks` — список объектов `Task` (композиция: задач без проекта не бывает)
- `created_at`

**Методы**
- `add_task(task)` — добавить задачу, вернуть её
- `remove_task(task_id)` — убрать задачу (и вернуть удалённую — пригодится для переноса)
- `get_task(task_id)` — найти задачу или `None`
- `list_tasks(status=None)` — все задачи либо только `active` / `done`
- `rename(new_name)` / `change_description(text)`
- `is_empty()` — есть ли задачи
- `progress()` — доля выполненных, например `0.0 … 1.0`

**Правила**
- `tasks` — внутренний список; снаружи отдаём копию или итератор, чтобы нельзя было
  обойти `add_task()` и подсунуть «чужую» задачу.
- Удаление проекта удаляет его задачи (каскад).
- `progress()` при пустом списке возвращает `0`, а не делит на ноль.

---

### 2.3 `User` — владелец проектов

**Атрибуты**
- `id`
- `name`
- `email` — уникальный, используется как логин
- `projects` — список объектов `Project`

**Методы**
- `create_project(name, description)` — создаёт проект, сам становится `owner`
- `remove_project(project_id)`
- `get_project(project_id)`
- `list_projects()`
- `all_tasks()` — плоский список задач по всем проектам (удобно для сводок)

**Правила**
- Пользователь не редактирует задачи напрямую — только через `Project`/`Task`.
  `User` — это «точка входа», а не «бог-объект».

---

### 2.4 `TaskManager` — сценарии использования

Не хранит предметных данных, а связывает объекты и репозиторий.

**Атрибуты**
- `users` — коллекция пользователей
- `repository` — хранилище (интерфейс)

**Методы**
- `register_user(name, email)`
- `create_task(user_id, project_id, title, **options)`
- `complete_task(user_id, project_id, task_id)`
- `move_task(user_id, from_project_id, to_project_id, task_id)` — перенос без потери `id`
- `delete_task(...)`, `delete_project(...)`
- `find_overdue(user_id)` — все просроченные задачи пользователя
- `search(user_id, text)` — поиск по названию/описанию
- `save()` / `load()` — через `repository`

**Зачем отдельный класс:** иначе `User` и `Project` обрастут логикой «а ещё покажи отчёт,
а ещё сохрани в файл». `TaskManager` — единственное место, где живут сценарии.

---

### 2.5 Вспомогательные объекты (v1 — по минимуму)

- `Tag` — пока просто строка; отдельный класс нужен, только если появятся цвет/описание.
- `Comment` — `id`, `task_id`, `author`, `text`, `created_at`. Откладываем до v2.
- `Filter` (стратегия) — `ByStatus`, `ByTag`, `ByDueDate`. Позволяет добавлять фильтры,
  не меняя `Project.list_tasks()`.

## 3. Как объекты взаимодействуют

```text
User 1 ──< Project 1 ──< Task
  │            │
  └── owner ───┘

TaskManager ──> User / Project / Task   (вызывает методы)
TaskManager ──> TaskRepository          (сохраняет и загружает)
```

**Ключевые связи**
- `User` **содержит** `Project` (агрегация: проект можно передать другому владельцу).
- `Project` **содержит** `Task` (композиция: задача живёт и умирает вместе с проектом).
- `Task` **не знает** о `Project` — не храним обратную ссылку, чтобы не было циклической
  зависимости и рассинхрона. При необходимости контекст передаёт `TaskManager`.

**Типичные сценарии**

1. *Создание задачи*
   `TaskManager` → `User.get_project()` → `Project.add_task(Task(...))` → `repository.save()`.
2. *Выполнение задачи*
   `TaskManager` → `Project.get_task()` → `Task.mark_as_done()` → сохранение.
   `Project` не лезет внутрь `Task`, он только отдаёт объект.
3. *Перенос задачи*
   `Project.remove_task(id)` возвращает объект → `Project2.add_task(тот же объект)`.
   `id`, `created_at`, `completed_at` сохраняются.
4. *Отчёт*
   `User.all_tasks()` → фильтр `is_overdue(now)` → сортировка по `due_date`.

**Порядок вызовов всегда сверху вниз:** `TaskManager` → `User` → `Project` → `Task`.
Обратных вызовов «снизу вверх» нет.

## 4. Что осознанно не делаем в v1

- Авторизация и пароли — только `email` как идентификатор.
- Совместная работа, роли, права доступа.
- Повторяющиеся задачи, подзадачи, зависимости между задачами.
- Уведомления и фоновые напоминания.
- Многопользовательская конкурентность (один процесс, один пользователь за раз).

Всё это — точки расширения, но не повод усложнять первую версию.

---

## 5. Критерии готовности модели

- [ ] Ни одно поле состояния не меняется в обход метода класса.
- [ ] `Task` можно протестировать отдельно, без `Project` и `User`.
- [ ] `Project` можно протестировать с фейковыми задачами.
- [ ] Хранилище можно заменить (файл → БД), не меняя доменные классы.
- [ ] У каждого класса одна причина для изменения.
